Contournement 2FA avec un code non lié

Ce lab a une seconde étape de connexion pour la 2FA, mais le serveur vérifie le code et le couple username/password de manière indépendante. Cela rend possible de mélanger ton code avec les identifiants de quelqu’un d’autre.

Rappel rapide

Un code 2FA doit appartenir au compte qui essaie de finaliser la connexion. Si l’application valide un code sans le lier à l’utilisateur, le second facteur n’en est plus un.

D’où vient la vulnérabilité

L’application vérifie le code et les identifiants séparément, puis autorise la connexion si les deux passent.

code_valid = conn.execute(
    "SELECT * FROM tfa_codes WHERE code=? AND expired=0",
    (code,)
).fetchone()

user_valid = conn.execute(
    "SELECT * FROM users WHERE username=? AND password=?",
    (username, password)
).fetchone()

if code_valid and user_valid:
    # connexion réussie

Comment fonctionne l’exploit

Déclenche un code 2FA pour ton propre compte, puis intercepte la requête de la deuxième étape et remplace les identifiants par ceux de la cible tout en gardant ton code valide.

Requête légitime de la 2e étape

POST /login2
username=user
password=password
2fa_code=483921

Requête modifiée

POST /login2
username=admin
password=adminpass
2fa_code=483921

Le code passe toujours parce que l’application vérifie seulement s’il existe. Les identifiants passent aussi, donc la connexion se fait en tant que admin.

Correctif

On lie la vérification du code au nom d’utilisateur, pour que le code doive appartenir au même utilisateur que les identifiants soumis.

code_valid = conn.execute(
    "SELECT * FROM tfa_codes WHERE code=? AND username=? AND expired=0",
    (code, username)
).fetchone()

Une fois la requête enrichie de username=?, un code émis pour user ne peut plus être rejoué avec les identifiants de admin.
