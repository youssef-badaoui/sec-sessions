Jour 4 / Lab 6

Race condition dans un virement bancaire

MiniBank lit le solde de l’expéditeur, fait un peu de travail supplémentaire, puis applique la mise à jour. Deux requêtes envoyées presque en même temps lisent toutes les deux le même solde, passent toutes les deux le contrôle, et soustraient toutes les deux — laissant l’expéditeur avec un solde négatif.

Rappel rapide TOCTOU

TOCTOU signifie time-of-check / time-of-use. Une race condition apparaît quand un contrôle et l’action basée sur ce contrôle sont séparés dans le temps et qu’un autre thread peut modifier l’état entre les deux. Sur le web, ça veut généralement dire deux requêtes HTTP qui font la course pour lire-puis-écrire la même ligne.

D’où vient la vulnérabilité

L’endpoint de virement fait le contrôle du solde et le débit en deux opérations séparées, avec d’autres requêtes au milieu.

# 1. LIRE le solde (time of check)
sender = conn.execute(
    "SELECT * FROM users WHERE username = ?", (user['username'],)
).fetchone()
recipient = conn.execute(
    "SELECT * FROM users WHERE account_id = ?", (target_account_id,)
).fetchone()

# 2. VÉRIFIER contre la valeur qu’on vient de lire
if sender['balance'] < amount:
    return redirect(...)

# 3. travail en plus — élargit la fenêtre de la race
conn.execute("INSERT INTO audit_log ...")

# 4. UTILISER (time of use)
conn.execute("UPDATE users SET balance = balance - ? WHERE username = ?", (amount, sender['username']))
conn.execute("UPDATE users SET balance = balance + ? WHERE username = ?", (amount, recipient['username']))

Le contrôle de l’étape 2 utilise sender['balance'] — une variable Python lue à l’étape 1, pas une lecture en direct. SQLite est en mode WAL donc des connexions concurrentes peuvent maintenir leurs propres snapshots de lecture en même temps. Deux requêtes entrent dans ce code, lisent toutes les deux balance = 100, passent toutes les deux le contrôle, et exécutent toutes les deux le UPDATE balance = balance - 100. La mise à jour décrémente toujours la valeur courante, donc la deuxième pousse le solde à -100.

Détail intéressant : remplacer UPDATE balance = balance - ? par UPDATE balance = ? WHERE ... avec une valeur pré-calculée rend la chose encore pire — les deux threads écriraient le même 0 et le solde du destinataire ne refléterait même pas correctement les deux virements.

Comment fonctionne l’exploit

On crée deux comptes (alice et bob) et on se connecte en tant qu’Alice. On copie l’id de compte 20 chiffres de Bob. On récupère le cookie de session depuis le navigateur et on tire une poignée de virements en parallèle.

Curls en parallèle

for i in $(seq 1 5); do
  curl -s -X POST http://localhost:5006/transfer \
    -H "Cookie: session=<alice-session>" \
    -d "target_account_id=<bob-account-id>&amount=100" > /dev/null &
done
wait

On rafraîchit le dashboard. On voit plusieurs virements alice → bob de 100 $ dans l’historique, le solde d’Alice négatif, et celui de Bob au-dessus de 200 $. Alice n’a jamais eu plus de 100 $.

Burp Intruder / Repeater

Dans Burp, on capture la requête de virement, on l’envoie à Repeater et on crée un groupe d’onglets. Clic droit puis Send group in parallel (single-packet attack). Cela aligne les requêtes dans un seul paquet TCP, ce qui maximise la chance qu’elles passent toutes le contrôle de solde avant que l’une d’elles n’écrive.

On garde le burst autour de 5–10 requêtes. Le serveur de dev de Flask est mono-process, donc des bursts énormes se transforment juste en réponses database is locked sans aider.

Correctif

Le contrôle et l’écriture doivent être une seule instruction atomique, et l’application ne doit valider la suite du virement que si cette instruction a réellement mis à jour une ligne.

# Débit seulement si le solde peut couvrir le montant
cursor = conn.execute(
    "UPDATE users SET balance = balance - ? "
    "WHERE username = ? AND balance >= ?",
    (amount, sender_username, amount),
)
if cursor.rowcount == 0:
    return redirect(url_for('dashboard', message='Insufficient balance'))

conn.execute("UPDATE users SET balance = balance + ? WHERE username = ?", (amount, recipient_username))
conn.execute("INSERT INTO transfers ...")
conn.commit()

Le WHERE balance >= ? déplace le contrôle dans la base, donc deux UPDATE concurrents ne peuvent pas réussir tous les deux sur le même solde de départ. Sur une base plus complète, on peut aussi utiliser SELECT ... FOR UPDATE dans une transaction explicite pour verrouiller la ligne de l’expéditeur le temps du virement.

Les race conditions ne concernent pas que l’argent. Le même schéma casse l’utilisation des coupons, les inscriptions sur invitation, les bypasses 2FA à usage unique, et les flux « payer en points ». Partout où on voit « vérifier X, puis faire Y », demande-toi si X peut changer entre la lecture et l’écriture.
