Account Takeover Through a Password-Update IDOR

The password-update endpoint reads two values from the request body — the target user id and the "old" password — and trusts both. The "old password" check is run against the session user, but the password is then written to the user id from the body. A regular user can change anyone's password.

Quick Reminder — IDOR

Insecure Direct Object Reference (IDOR) happens when an endpoint operates on an object identifier supplied by the client without verifying that the caller is allowed to act on that object.

In this lab the impact is full account takeover: the regular user rewrites the admin's password and then logs in as admin to read a secret only admin can see.

Where the vulnerability comes from

The handler validates old against the session user but writes to the uid from the request body. The mismatch is the entire bug.

@app.route("/update_password", methods=["POST"])
def update_password():
    data = request.get_json(silent=True) or {}
    uid = int(data.get("id", 0) or request.form.get("id", 0))
    old = data.get("old") or request.form.get("old")
    new = data.get("new") or request.form.get("new")
    cu = current_user()
    if cu and cu["password"] == old and uid in users:
        users[uid]["password"] = new
        return ...

The HTML form ships a hidden id field equal to the session user. Hidden form fields are user-controlled — anything the browser submits, an attacker can edit.

Exploitation

Log in as the regular user, then submit the password-update form with id=1 (the admin) and your own current password as old.

Login as the regular user

username=user
password=user123

Take over admin

curl -i http://localhost:5010/update_password \
  -b cookies.txt \
  --data "id=1&old=user123&new=pwn3d"

Log out, log back in as admin with the new password, then visit /admin/secrets.

The Fix

Never accept the user identifier from the request body when the action targets the caller's own resource. Derive it from the session.

@app.route("/update_password", methods=["POST"])
def update_password():
    cu = current_user()
    if not cu:
        return redirect(url_for("index"))
    old = request.form.get("old")
    new = request.form.get("new")
    if cu["password"] != old:
        return "forbidden", 403
    users[cu["id"]]["password"] = new
    # password gets stored hashed in real apps
    return redirect(url_for("profile"))

Two reinforcing rules to remember:

  • The session is the source of truth for "who is acting" — never the request body.
  • If an endpoint must accept a target id (e.g. an admin acting on someone else), authorize that the caller is allowed to act on that target.
